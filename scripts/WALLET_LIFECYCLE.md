# Scenario-wallet lifecycle

Claude (AI), 2026-11-05. Answers the board request x-20261104-scenario-wallet-lifecycle-r1 (testbed issue 15, comment 6636628939) and Codex's exact-head review of the first head (comment 6643854505). Operator requirement, as relayed: scenario wallets run from keys the orchestrator controls, and they empty back to the funding wallet at the end.

**Scope: this is a mock-tested component, not completion of the requirement.** No current runner calls it. The obligation stays open until a runner is wired (see the integration proposal below).

`wallet_lifecycle.mjs` is decision and journal logic with injected ports. It imports no network library, holds no key, never signs and sends nothing itself. A runner supplies ports that wrap its own signer. `test_wallet_lifecycle.mjs` (32 tests, in-memory chain, no network) runs with `node --test scripts/test_wallet_lifecycle.mjs` and is part of `tools/check.py`.

## The journal is private, not public evidence

It stores the signed raw transaction of every unsettled sweep, on purpose: a retry rebroadcasts the identical bytes and never signs again. Keep the file private (it is written mode 0600, atomically, with fsync of the file and of its directory). `publicView(journal)` drops the raw bytes and is the only form that may leave the runner. Errors from providers or signers are never stored, because their text can carry credentials or private endpoints; only a short code is (`port_error`, `save_error`). A test checks a credential-bearing error message does not reach the journal.

## Before a run

`verifyControl` asks the runner whether the orchestrator controls each scenario signer, without signing to prove it, and records `control_ok` or `control_check_failed`. A failed wallet is `signer_lost` before any funds are placed. Wallet ids must be non-empty, unique and well-formed, addresses must be unique, and the funding wallet may not be a scenario wallet. A loaded journal is validated the same way, so a tampered or inconsistent file is refused.

## At the end (success, failure, timeout or interruption)

`runCleanup` sweeps each wallet's test tokens to the funding wallet, then returns recoverable native gas. It is safe to call again after any interruption and always reads fresh balances (a cached `empty` or `swept` closes nothing). `terminalVerify` re-reads every token balance last, so a later deposit reopens that wallet.

| Wallet state | Meaning | Counts as |
| --- | --- | --- |
| `empty`, `swept` | nothing left, or swept and the receipt verified | emptied |
| `dust_accepted` | at or below the declared dust threshold | named exception |
| `locked_contract` | an address that is a contract holding tokens | named exception only if its address is in the approved list; otherwise open |
| `needs_gas`, `signer_lost`, `failed`, `unknown`, `pending` | not done | open |

Gas return: `returned` (including nothing left), or a `residual` at or below the return fee or the gas dust, which is a named exception. `signer_lost`, `failed`, `unknown` and `pending` are open.

Run status: `failed_cleanup` while anything is open, the gas phase was skipped or not run, or a journal write failed; `pending_reconciliation` when everything is settled but no reconciliation has been recorded; then, after a matching reconciliation, `closed` (every wallet emptied, no exception) or `closed_with_exceptions` (every remainder is a named, approved residual). A failed reconciliation is stored, persisted and sticky: `finalize` and further cleanup passes keep `failed_cleanup` until a later reconciliation matches. Skipping the gas phase is allowed but recorded, and such a run can never close.

## Idempotency, durability, unknown outcomes

- The sweep's hash and signed bytes are written to the journal before the first broadcast. If that write fails, nothing is broadcast and the wallet is `unknown`.
- A save failure after a broadcast marks the journal `persistence.failed` and the run `failed_cleanup`; the in-memory and last durable intents are kept, never overwritten by a generic unknown state. Resuming from the last durable journal checks the recorded hash, rebroadcasts the identical bytes if needed, and does not sign again.
- Only the receipt decides an outcome, and the receipt must bind to the prepared intent: from, to (the configured funding wallet), amount and nonce, and the token when given. A receipt for another recipient or amount is a `mismatch`; the wallet stays `unknown`, the run open.
- No rebroadcast happens unless the journal can be saved first: a retry that cannot persist returns `unknown` and sends nothing (tokens and gas, any number of passes).
- A receipt `mismatch` is sticky. Later passes, a reload or a zero reconciliation do not clear it; only `resolveMismatch(journal, id, {evidence, decidedBy})` records a human disposition (`dispositioned`) and that is stored and persisted.
- A reconciliation is bound to a fingerprint of the journal. If a later sweep changes the journal, the stored reconciliation moves to `staleReconciliations`, the status returns to `pending_reconciliation`, and a new cumulative reconciliation is required.
- A terminal status is never returned unless its final save succeeded: if the last write fails, `finalize`, `reconcile` and `terminalVerify` return `failed_cleanup`, and the last durable file is the recovery point.
- A journal written by an earlier version (reconciliation without a fingerprint) is migrated on load: the old reconciliation is kept as a legacy stale record and the run is `pending_reconciliation` until a fresh cumulative one is recorded.
- The journal is saved through a unique, exclusively created temp file forced to 0600 (an existing or world-readable `.tmp` is never reused), written in full with a byte-count loop (zero progress or an error fails the save), renamed into place, and the directory is fsynced.
- An error from `broadcast` is never read as failure. A sweep not yet mined after one identical rebroadcast stays `unknown`.
- Persistence is required. `runCleanup`, `verifyControl` and `reconcile` throw unless given a `save` function (an explicit `ephemeral: true` exists for tests only).

## Signed bytes and the pre-broadcast verifier

**One byte format.** A signed transaction is stored as one canonical string: `0x` plus lowercase hex of whole bytes (`canonicalRaw`). A prepare port may return a `Uint8Array` or `Buffer`; it is converted before anything is stored, so the journal holds one lossless form that survives a JSON reload, the ordinary intent, a late orphan and a resumed rebroadcast alike. Text that is not hex, odd-length hex, an empty value or an oversize value is not accepted as a signed intent: the component stores nothing and sends nothing (`prepare_output_invalid_not_sent`), and the runner keeps its in-flight marker (it cannot show nothing was signed).

**A mandatory verifier before any broadcast.** The component takes a `verifyPrepared(raw, { kind })` port. It must decode the serialized signed transaction itself and return what the bytes say: kind (`erc20` or `native`), recomputed hash, recovered signer, chain id, nonce, recipient, amount, `maxFeeWei`, and for a token transfer the contract and a native value of zero. The component, not the port, compares each field with the intent it requested (signer = the wallet, hash = the recorded hash, chain = the run's chain, nonce, recipient = the funding wallet, amount, token contract = the run's token, fee at most the named `maxFeeWei`). The intent is stored first, so the private bytes are never lost; then the gate runs. A missing verifier, an unnamed chain, token or fee bound, a decoder error, an invalid result or any difference leaves the intent stored as `unverified` (with a short `verifyReason`), the wallet `unknown` and the run open, with zero broadcasts. A resume verifies again before it sends, for initial and resumed token and gas sends alike, and never signs again. The receipt check after the fact stays as a second line, not as the prevention. This module still holds no real verifier: a real decoder (a transaction parser that recovers the signer and recomputes the hash) is a port the runner's owner supplies, and the module is not claimed safe for real use until one exists and is reviewed. The runner requires the port and `maxFeeWei` (a bigint, part of the run's identity) or refuses the configuration.

## The cryptographic decoder (`scripts/lifecycle_verifier/`)

`verify_prepared.mjs` is the real implementation of the `verifyPrepared(raw)` port for one narrow form. It takes only the canonical signed bytes and derives every field from them (a second argument is ignored): the hash is the keccak256 of the exact bytes, the signer is recovered from the signature, and the transfer is decoded from the calldata. It is given no expected values and echoes none. Supported: an EIP-1559 transaction with an empty access list and a low-S, in-range signature in canonical encoding, carrying either one ERC-20 `transfer(address,uint256)` call (exactly 68 bytes of calldata, zero address padding, zero native value reported) or a plain native transfer with empty calldata. Rejected, with a short reason: legacy, EIP-2930, EIP-4844, EIP-7702 and unknown types, unsigned or unparseable bytes, trailing bytes and alternate encodings (a re-serialization must equal the input; a non-minimal integer is the tested example), contract creation, any other selector or extra calldata (approve, transferFrom, multicall, batch), dirty address padding, a non-empty access list, a high-S twin, zero or out-of-range r or s, zero gas, a priority fee above the cap, and anything over 4096 bytes. The decoder does not claim to reject every contract-wallet situation: transaction bytes cannot show the current token implementation, the recipient's code, whether the sender already carries an EIP-7702 delegation (rejecting a type-4 envelope says nothing about an existing delegation on a type-2 sender), the current balance or nonce, or receipt finality. Those are chain-state checks for the adapter that must precede activation. `maxFeeWei` is gas times the fee cap: the EVM execution-fee ceiling only. It is NOT an all-in cost bound for Base Sepolia (the L1 data charge and any operator charge are separate, chain-specific components it does not calculate); a real gas-return budget needs a pinned all-in fee and reserve policy before any activation. The component then compares those decoded fields with the intent it requested.

It uses viem (pinned to 2.57.14 in a script-local `package.json` and lockfile; install with `npm ci --ignore-scripts` in that folder; no root dependency), a library already used by this repository's other verifier. It holds no key and opens no connection. Tests generate throwaway keys in memory and sign fixtures locally; they cover each case above, mutations of every check, and the component's gate fed with really signed transactions (wrong recipient, amount, token contract, chain, nonce, native value, fee and signer all stop before any broadcast). `tools/check.py` runs them through `run_tests.mjs`, which prints `SKIPPED` (not a pass) when the dependency is not installed. The run_tests.mjs wrapper exits 0 with SKIPPED when the dependency is absent, so release evidence must show that the 24 decoder tests actually ran at the exact head; an aggregate check that is green is not that evidence. This is local verification only: it does not install custody, wire a runner or authorise any live action.

## Chain-state gate, fee policy and the custody boundary (checkpoint B, local only, disabled)

**Chain-state gate** (`scripts/lifecycle_verifier/chain_state.mjs`). DELIVERED CODE, NOT YET CALLED: neither `wallet_lifecycle.mjs` nor `lifecycle_runner.mjs` uses it, so it guards no send today; a later step must consume it as a mandatory port (B2), and that step stays held until its exact head is accepted. The decoder cannot show what the bytes do not carry, so this second gate is meant to run after it and before every send and rebroadcast, with a receipt step after inclusion. It uses an injected `rpc` port, opens no connection and holds no key. Provenance and race limits, stated rather than claimed away: `rpc.providerId()` is an assertion by the injected port, not independent proof of which route answered, so the real provider adapter must prove the approved route and the block-hash semantics; every state read of a pass is pinned to one block hash (re-read at the end; a changed hash holds the send) EXCEPT the pending transaction count, which a node cannot pin, so that read is a separate freshness and race limit and exclusive custody (one signer for these wallets) is the control for it. Every missing, null, malformed or thrown answer holds the send with a sanitized reason (provider text is never echoed): nonces and counts must be integers, balances and fee quotes exactly 32-byte words or quantities, code and storage must be well-formed, block fields must be a 32-byte hash and integers, and `ok:true` needs every read and a complete envelope; zero is a value, a missing answer is not. It checks: the provider reports an approved id and the pinned chain id; the anchor is fresh and not in the future beyond a stated skew (`maxFutureSkewSec`, at most 60 s); sender and recipient have NO code (an EIP-7702 delegation designator, `0xef0100` plus an address, is classified `delegated` and held, as is any contract; the supported wallet policy is a plain account only, so a delegation on a type-2 sender is caught here, not by the envelope type); the token's runtime code hash equals the pinned hash and, for an EIP-1967 proxy, so do the implementation read from its slot and its code hash; latest and pending nonces equal the intent's; the token balance covers the amount. The between-check-and-inclusion window is shortened, not closed; a delegation or an upgrade that lands after the last read and before inclusion is residual risk.

**Base all-in fee policy.** `gas x maxFeePerGas` from the decoder is only the execution-fee ceiling. The envelope the gate computes is that ceiling, plus the L1 data fee quoted by the OP-stack gas price oracle at the anchor block for the exact serialized payload (multiplied by a stated margin, `l1MultiplePpm`, at least 1x, rounded up), plus an explicit operator-fee bound from configuration (`operatorFeeBoundWei`; there is no default, because zero must not be assumed for a configuration nobody has verified). Three numbers are kept apart: the execution ceiling, the all-in estimate, and the separately authorized maximum exposure (`maxExposureWei`); an envelope above the authorization holds the send, so does an oracle that does not answer, an incomplete policy (every send is refused and the missing keys are named) and a native balance below envelope plus reserve (plus the value, for a native transfer). A margin on an estimate is not a protocol cap and is not described as one. A gas return moves balance minus the whole envelope minus the reserve (`gasReturnAmount`), never balance minus the L2 ceiling alone. After inclusion `reconcileReceipt` binds the receipt to THIS transaction (the receipt's transaction hash equals the decoder's recomputed hash, its sender is the wallet and its outer target is the token contract for a token sweep or the funding wallet for a native transfer, and the transaction fetched by hash has the same sender, target, nonce, value and exact calldata), requires the envelope that `preflight` produced (it carries a binding to the intent hash, provider, chain, anchor block and a digest of the policy, and any other envelope or none holds), requires every actual cost component (an operator fee the receipt does not report counts as zero only when the policy names `verified_not_applicable` evidence, and a zero operator bound itself needs that named evidence), checks that the actual total (L2 plus L1 plus operator) fits both the envelope and the separately authorized exposure, that the sender's native balance fell by exactly the actual fee (plus the value for a native transfer), exactly one Transfer log from the pinned token with the right sender, recipient and amount and no foreign logs (none at all for a native transfer), and re-validates the inclusion block and the head at the end, so a block that is replaced, or a head that moves backwards or changes hash, while the check runs holds; a missing or NaN head, or one in the future, never satisfies the confirmations. Nothing in this configuration is evidence about Base Sepolia itself: the policy values, the oracle address and the operator-fee bound must each be established against the pinned chain by the owner, at a recorded block, before any activation, and are not copied from another network.

**Custody and provider boundary (execution disabled).** Requirements for the real signer and provider adapters, none of which exist in this change: (1) the signing key is held only by the orchestrator's custody component for the lifetime of the run, is never written to the journal, a log, a checkpoint, a receipt or any public output, and a raw signature never leaves that component except as the signed transaction bytes the journal stores privately; (2) the signer port returns bytes, never a key, and proves control without signing a value (`controls`); (3) prepare, send and receipt are supervised: every call has a timeout, a timed-out or rejected prepare keeps the durable in-flight marker, an uncertain effect is retained and never retried as a new signature, and a restart resumes from the byte-exact journal; (4) the provider adapter pins the chain id and an approved provider identity, returns block-pinned answers, and reports every failure as a failure, never as an empty or zero value; (5) there is a current control proof before any funding, so no wallet is funded that the run cannot sweep; (6) code existence is separate from installation: installing a custody component, supplying keys, naming an approved provider or enabling the runner each needs its own authorization and acceptance evidence, and none follows from this code or from the execution-owner state; (7) there is still no orphan-disposition procedure, so an unknown orphaned intent stays open and blocks closure. The disabled gate here is exercised only against an in-memory chain with generated throwaway identities.

## What this does not do

It does not hold or derive keys, does not top up gas for wallets that lack it (`needs_gas` is reported with the amounts; a top-up is a separate, separately authorized transfer), does not recover anything by itself, and makes no real transfer. Historical balances are a separate matter: see `evidence/test-usdc-reconciliation-20261104/README.md` (signer control and the contract's withdrawal conditions are unverified).

## Runner adapter (disabled by default; local fixtures only)

`scripts/lifecycle_runner.mjs` is the one place that decides when the component runs around a scenario. It imports no network library, holds no key, signs nothing. A runner passes `ports` that wrap its own signer. It is off unless the caller passes `enabled: true` (the environment switch is `OMNEQUA_WALLET_LIFECYCLE=1`, read by `lifecycleEnabled`); when off it returns `{status:'disabled'}` and calls no port, creates no file and installs no handler.

Order when on: validate the roster; take a single-owner lock beside the journal; if a journal exists, **resume** (never fund again, never rerun the scenario, go straight to cleanup from the last durable intent); otherwise verify control of every signer and **refuse funding** before any transfer if one is missing (`refused_control`, complete inventory kept); record phase `funding` durably, fund (an error or crash here counts as funded); run the scenario with a timeout and an abort signal (SIGINT/SIGTERM abort it); then **always** enter terminal cleanup once: sweep tokens, return gas, re-read every balance, reconcile the funding wallet's gain against settled receipts (the funding balance before the first sweep is stored in the journal so a resumed run reconciles cumulatively). Supervision and ownership: funding and the scenario run under a timeout and the abort signal, and after a timeout or abort they must actually **settle** within `quiesceMs` before anything else happens; if they do not, the run returns `unquiesced` (journal `failed_cleanup`, phase `unquiesced_funding` or `unquiesced_scenario`), runs no cleanup, closes nothing and keeps the lock while this process lives (it is released only when the work really settles; a later run then resumes). Every port call during cleanup is bounded by `portTimeoutMs`. A timeout rejects the caller's wrapper but does not stop the underlying call, so effect calls (prepare, broadcast) are also **tracked**: after one times out, no further effect is launched in that pass (they fail at once), the run waits up to `quiesceMs` for the outstanding calls to really settle and then reconciles from receipts (at most `maxCleanupPasses`), and if they do not settle the run returns `unquiesced` (`unresolved: 'cleanup_effects'`), keeps the lock until they do, and closes nothing. Before any prepare (signing) call a **durable in-flight marker** is written; it is cleared by the same write that records the returned intent, so after a crash or a failed save the durable file still says a signature may exist. A prepare that REJECTS does not clear it either: a generic rejection (or a timeout) does not show that signing did not happen, so an unknown prepare failure keeps the marker, halts further effects and ends the run `failed_cleanup`; only a `PrepareNotStarted` rejection (a typed error a port throws when it can show signing never began) or a COMPLETE signed-intent result (a non-empty hash and signed bytes in the canonical form above) clears it, and a fulfilled but malformed result (undefined, null, `{}`, a hash without bytes, wrong types), in time or late, is treated like an unknown failure, and the marker write itself failing means the signer was never called. Consequently and a plain resume refuses (`orphans_unresolved`) instead of signing again. A late result is made durable before ownership is given up: the lock is kept while that write keeps failing (bounded retries, then the lock still stays and the durable marker makes any later resume fail closed). A prepare that returns after its timeout produced a signed transaction nobody recorded: it is kept as an **orphaned intent** in the private journal (raw bytes private, hash and nonce in the checkpoint), is never broadcast, blocks closure, and stops all further signing for that run (`orphans_unresolved`) until a reviewed procedure dispositions it (none is provided). Reads that time out simply leave the wallet `unknown`. The journal stores the exact identity of the run (sorted roster of ids and addresses, funding wallet, chain id, token, dust and gas policy, approved contracts); a resume with any difference, or a journal without an identity, is refused before a single port call. `chainId`, `token` and `maxFeeWei` are mandatory. The lock is published complete (written and fsynced to a private temp file, then hard-linked into place), so no entrant sees a partial lock; a malformed lock fails closed; a lock whose recorded pid is dead is reclaimed under a guard only if it is still the same lock; release removes the lock only if it still carries our token. Only work done inside the scenario promise (or the funding call) counts as covered by the quiescence rule: work a scenario starts and forgets is outside the contract and must register with the scenario.

Exit codes: 0 closed after a successful scenario, 2 anything else, 3 closed with named exceptions, 130/143 interrupted. A resumed run never reports scenario success. Receipts must state the expected chain and token when the runner names them. `checkpoint(journal)` and `publicReport(journal)` are the only forms that may leave the process (no raw bytes, keys or error text).

Run the local tests (generated unfunded identities, a file-backed in-process chain, disposable child processes for signals and SIGKILL at each durable boundary; no live credentials, RPC or transfers):

    node --test scripts/test_lifecycle_runner.mjs scripts/test_wallet_lifecycle.mjs

What this is not: no current runner calls it, and the ports that wrap a real signer (for example the cold start's derived keys) are not written. Wiring that, funding real scenario wallets and the sweep transactions remain separately authorized, as listed under the integration proposal below.

## Integration proposal (disabled by default; nothing below is in this change)

1. **Ports adapter, disabled by default.** (The generic runner adapter above exists; this is the part that is still a proposal.) A module `coldstart-lifecycle-adapter.mjs` next to `coldstart.mjs` builds the ports from the runner's own ethers provider and derived signers (`controls` = the derived address equals the roster address; `prepareSweep` and `prepareGasSweep` sign locally and return hash and bytes; `broadcast` sends bytes; `receipt` decodes the transfer and returns from, to, amount, nonce). A `--lifecycle` flag, default off, enables it. With the flag off the runner behaves exactly as today.
2. **Wiring.** Before funding: `verifyControl` over the roster; refuse to fund if any signer is missing. Terminal handler for success, failure, timeout and SIGINT/SIGTERM: `runCleanup`, `terminalVerify`, `reconcile` against the funding wallet's before and after balances, `saveJournal` to a private path outside the evidence folder; publish only `publicView`.
3. **Tests.** The adapter gets mock-provider tests for the same failure paths (lost signer, no gas, RPC failure, duplicate retry, uncertain sweep, wrong recipient, save failure) and a test that with the flag off the runner makes no extra call.
4. **Exact authorization blocker.** Not a generic credential-bearing-code concern. Two specific approvals are missing: (a) permission to execute any workflow that reads the existing `TEST_WALLET_PRIVATE_KEY` secret for a purpose other than the already-run funding scripts (a new use of the credential, even read-only); and (b) the operator-queue authorization for the sweep transactions themselves (testnet token and gas transfers from role wallets), which the lifecycle request keeps separately gated. Neither is requested here. Writing and reviewing the adapter and its mock tests needs neither.
