# Durable local policy prototype

Codex (AI), November5 2026. Implemented in durable.py; independently testable with `python -m unittest -v test_durable`. This is a local SQLite prototype, not deployed behavior. It contains no RPC, signer, sender, model call or live-grant API. `execution_permission()` always returns allowed=false. The old bounds.py is deliberately retained so its failure reproductions remain visible.

## Implemented controls

- **Persistent accounting:** SQLite transactions use BEGIN IMMEDIATE, WAL and synchronous=FULL. All workers using the same database serialize reservation changes. Amounts are integer micro-units. Principal, recovery, pending transaction, evidence and policy configuration survive process restart. Missing ledger files fail closed unless explicitly initialized; reopening with changed limits is rejected. Never initialize a fresh database to recover a missing ledger.
- **No automatic retries:** reserve creates a durable intent and prepare_attempt records one exact anticipated transaction hash before hypothetical submission. Repeated exact calls are idempotent; changed payload/hash fails. Preparing a new attempt rechecks the stored expiry against an explicit clock value. Unknown chain outcome stays PENDING with its full reservation. Only a sufficiently confirmed observed revert releases net exposure; gross issuance allowance remains consumed. This prototype never submits anything.
- **Recovery is not a supplied number:** apply_repayment accepts only an intent and receipt lookup key. It obtains normalized facts from an injected reader, checking chain, success, canonical block/depth, pool/token, loan/borrower binding, principal amount and transfer source/destination. Pool self-transfers cannot count as repayment; funding must come from the pool. Partial recovery cannot exceed the remaining principal. A transfer including interest does not turn that interest into principal recovery.
- **One allocation per event and token-transfer log:** unique database constraints cover both keys. Even a second fabricated repayment event pointing at the same transfer cannot credit another loan. The recovery update and receipt allocation commit atomically. Exact replay returns no new credit, including after restart.
- **Repayment farming does not grow limits:** frozen per-controller/group/global NET ceilings and separate lifetime GROSS issuance ceilings both apply. Repayment reduces net exposure but never increases the gross allowance, changes an identity/controller, resets evidence, raises a score or creates a new policy epoch. This intentionally limits legitimate repeat borrowing too; expansion requires an independently reviewed future migration backed by explicit authority, not an automatic reputation multiplier.
- **Reconciliation and incident hold:** before further reservations or preparation of an attempt after observed funding, and before accepting recovery, recheck prior funding/repayment block hashes through the reader. A mismatch persists an incident that blocks new reservations even if the hash later changes back. Defaults do not erase exposure; authentic partial/late recovery can reduce it. There is no automatic incident-clear or ledger-reset API.

## What the reader must establish

No reader is configured by default. The tests use a synthetic Reader, so their observations are not evidence that any real transaction occurred. Observation is a proposed semantic interface, NOT the canonical deployed contract ABI. A future executor must additionally revalidate current consent/revocation, evidence and affordability at action time, use a trusted clock, and bind the final signed sender/nonce/call/policy to the intent. Stored consent alone is not current authorization. A real adapter must independently establish receipt and log authenticity, correct chain and block, loan-scoped net principal recovery, matching token movement and immutable event indexes. Caller assertions, an LLM, a backer's reputation and a provided JSON receipt are not reader implementations.

The complete adapter also needs reviewed canonical ABI/wiring/proxy identity; finality and reorg policy; bounded current head freshness; consistent observations from the required independent sources; evidence of effective pool balance movement; and handling of multiple transfers/repayment events, refunds, third-party payment, fees and token anomalies. This conservative prototype consumes an entire matching transfer log for one recovery; it cannot split a transfer among loans. It rejects rather than guesses when these bindings are unavailable. No claim is made that12 confirmations is universally safe.

## Tests and remaining acceptance gates

Tests exercise independent SQLite connections racing for the same cap; restart with pending reservations; changed-intent/hash replay; missing reader; wrong chain/token/destination/loan; unsuccessful, shallow and noncanonical receipts; partial/default/late recovery; duplicate allocation; frozen policy; lifetime farming limits; and persisted reorg holds. A subprocess exits after committing PENDING, leaving exposure reserved. A second subprocess is terminated inside the recovery transaction after its balance update but before receipt insertion; restart shows neither partial change survived, and the subsequent exact retry credits recovery once. An SQL fault additionally checks rollback on unique-transfer conflict and insertion failure.

These tests validate local transition behavior under SQLite/filesystem guarantees. They do not prove durability under storage loss, tampering, unsafe filesystem semantics, restored stale backups or multiple independent database copies. Production must bind one authoritative ledger to its issuer, restrict database administration, manage backups/migration and independently reconcile issued chain exposure before any executor is enabled. Starting a second database is not horizontal scaling. The global gross ceiling protects only reservations recorded in that authoritative ledger; it cannot constrain an unrelated signer.

Actual granting remains disabled. Integration requires current source-owner acceptance, review of the exact application changes, a live read adapter with verified contract semantics, crash/retry and reorg tests against an authorized canonical test deployment, and reviewed wallet lifecycle controls. The existing shadow patch and current app branding are unchanged. Human consent/storage/facilitator and real repayment-validation gates remain separate.

Wallet lifecycle remains a separately owned dependency: [PR441 review6647410786](https://github.com/scottonchain/microcredit-agent-testbed/pull/441#issuecomment-6647410786) reports final-save false closure, stale legacy reconciliation and unsafe existing-temp-file permissions. The existing wallet owner/reviewer must resolve those at an exact reviewed head before wallet recovery integration or any live campaign. This change neither modifies that component nor treats its passing mocks as acceptance.

Review response: the independent reviewer reproduced the supplied tests, added concurrent-overpayment, concurrent duplicate-receipt and unavailable-history regressions, and found the preexisting-reservation incident bypass. That transition is now held inside the transaction; a stored-expiry recheck was also added before preparing a new attempt. All22 current durable cases pass locally. Current-consent validation and final signed-transaction binding remain mandatory future executor gates, with no live executor installed.
